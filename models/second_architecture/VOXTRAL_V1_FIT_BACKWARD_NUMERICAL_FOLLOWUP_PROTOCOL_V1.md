# Voxtral old-FIT backward numerical follow-up: prospective v1

**Frozen design, 18 November 2026. Protocol only; no model run or v2 efficacy claim.** This is a diagnostic of the [audited old-FIT backward pilot](VOXTRAL_V1_FIT_BACKWARD_INDEPENDENT_RESULT_REVIEW.md), not an extension of its findings to the fresh v2 corpus. The prior `animal_08|piper|fit_chosen` beaver→monkey, `word_0`, α=.025 pilot produced connected BF16 VJPs, but its four-coordinate local predictions were about 0.001 in norm while measured LM29 changes were 0.14–0.28. The rowwise realized-edit contraction was comparably inaccurate. The old pilot had **no Jacobian-prediction efficacy gate**; its 10% edit-fidelity mark was a reporting diagnostic. We do not treat that run as a failed v2 gate.

## Fixed case and question

Use only the same two pinned *v1 FIT* WAVs, one-word prompt, nominal `word_0` masks (encoder31 rows 96–107; projector rows 24–26), model `mistralai/Voxtral-Mini-3B-2507@3060fe34b35ba5d44202ce9ff3c097642914f8f3`, and four raw prompt-final LM29 coordinates `0,1,2,3`. Pin and verify the original pilot `result.json` SHA-256 `d4ccfd213cf3a5ebebd3a7c0ecebab691dc15632f61076669d7535bd58154ebe` and `details.pt` SHA-256 `1bc49aa650b96c7ac6cb2f545da98e198edfa18998ebae8dc263c70ad5ad7b3c`; read them only to reconstruct the frozen FP32 direction `δ_s = mean_rows(H_donor,s) − mean_rows(H_recipient,s)` at each site. Reuse the old FIT corpus/checkpoint/processor hash verification. Before model load, pin the installed Transformers source SHA-256 values: `modeling_voxtral.py` `2d3ec9d78c469b77c42a8d5ba258185fb1c58f4c2c7bf6007ec724436dfc7056`, `processing_voxtral.py` `239e84657d1a0287ab27a540c946a787a69b4b0bf45727d6b24bee21ccec0296`, `feature_extraction_whisper.py` `dcce2e7820be059e657a9e12a60e8a55cfd37b1a82ee202ca15fc7d0934374cb`, and `modeling_llama.py` `affc6a4ab36b562a6b4c90b84c4e7939c5417a69ad7bd37e858be5583f189830`. Do not open the fresh v2 corpus, its development results, or locked-test inputs or answers.

The question is whether the disagreement comes mainly from BF16 source/target quantization, unstable repeated forwards, or a finite edit outside the local linear regime. These are diagnostic alternatives, not assumptions. Keep the old pilot's natural/grad/no-grad baselines distinct; its four selected `no_grad−grad` coordinates were nonzero, while its zero-patch coordinates equaled the clean grad-path coordinates. Do not use a no-grad state as the denominator for a grad-path intervention.

## Two prespecified arithmetic arms

Run these as **separate, fresh one-shot processes** so an FP32 load cannot inherit BF16 allocator state. Both use the identical pinned WAVs, prompt, sites, rows, fixed direction `δ_s`, alpha schedule, SDPA implementation, and hook locations. No autocast, sampling, weight change, or model fine-tuning. Freeze parameters. Capture the prepatch source rows and the complete prompt-final LM29 vector on every forward; record hook counts, shapes, dtypes, source hashes and terminal hashes.

1. **BF16 reference.** Load the pinned checkpoint with BF16 runtime weights and activations. On the clean recipient graph, detach encoder31 into a differentiable BF16 leaf, keep the projector connected downstream, and take four VJPs with respect to both sources from the same graph. Require BF16 VJP outputs. Convert selected VJP rows to FP32 for storage/contraction; this does not restore lost BF16 precision. At each patch forward, compute `H'_j = BF16(H_j + αδ_s)` and the *actual* FP32 row edit `e_j = FP32(H'_j) − FP32(H_j)` from that forward's prepatch source state.
2. **FP32 arithmetic control.** Load the same BF16 checkpoint **upcast to FP32** and run the whole encoder, projector and LM in FP32. Assert FP32 parameters, hooked source/target states and VJPs; if any component silently uses BF16 or the full model cannot fit, record an invalid/resource-limited arm with an error receipt and do not substitute mixed precision. This control changes forward arithmetic; it does **not** recreate unquantized pretrained weights. Use the same frozen FP32 `δ_s` from the prior sidecar and set `H'_j = H_j + αδ_s` without a BF16 cast. Recompute the four local VJPs at this arm's own clean recipient state. Record its natural suffix IDs, but do not require equality with the BF16 suffix: a difference is an arithmetic-mode observation, not a reason to hide the numerical measurements.

For both arms, the encoder31 hook must feed the ordinary projector and the LM29 target in one graph; do not compare separately recomputed or detached projector paths. The nominal source edits are uniform over selected rows. Keep encoder31 and projector as **separate interventions**. Require one source/target invocation each on each no-cache prompt forward and the expected source shapes `[1,1500,1280]` and `[375,3072]`, LM prompt shape `[1,396,3072]`. Save exact IDs of natural and passive greedy 32-token suffixes and require their within-arm parity. The BF16 arm must also match the prior saved natural suffix; the FP32 arm need not.

## Frozen edit grid and repeatability control

Use nonzero alphas `A = {−0.1, −0.025, −0.00625, +0.00625, +0.025, +0.1}` and an exact α=0 patch. For each source site independently, perform **three** cycles of six paired no-cache forwards. In each pair, run an α=0 patch immediately before the nonzero α patch, with the same grad-enabled hook path. Cycle 1 order is `(+.00625, −.00625, +.025, −.025, +.1, −.1)`; cycle 2 reverses that order; cycle 3 repeats cycle 1. This fixes 18 zero/nonzero pairs = **36 prompt forwards per site, 72 per arm**, plus one donor capture, one clean grad graph with four VJPs, three additional clean no-grad targets, and two greedy generations per arm. Every α=0 source edit must be exactly zero in that arm's dtype. Record each paired zero terminal vector, edited terminal vector, prepatch selected source rows, realized edit `e_j`, and elapsed time. A source or target baseline that changes between pairs remains in the analysis as measured variability; do not discard or silently renormalize it.

## Metrics and interpretation

For site `s`, target coordinate `k`, alpha `a` and repeat `r`, the local rowwise prediction is `p_s,k(a,r)=Σ_j FP32(g_s,k,j)·e_s,j(a,r)`, using that arm's **one clean-state VJP** and that forward's actual edit. Also compute the uniform-row approximation `(Σ_j g_s,k,j)·mean_j(e_s,j)`, the ideal `aδ_s` contraction, edit norm, mean-fidelity ratio, row-nonuniformity ratio, and fraction of selected source elements unchanged by the cast. The paired measured change is `d_s,k(a,r)=FP32(z_s,k(a,r))−FP32(z_s,k(0,r,a))`; save all 3,072 terminal coordinates before selecting the four. FP32 storage of BF16 outputs is only for subtraction and archiving.

Report all three repeat vectors and their coordinatewise median for each alpha/site/arm. Compute absolute `L2(p−d)` and `L2(d)`, and a relative error using denominator `max(L2(d_median), N_s, 1e−6)`, where `N_s` is the largest four-coordinate `L2` distance between any two of that site's 18 paired-zero terminal vectors. Mark `L2(d_median) < 3N_s` as **below repeatability resolution**, rather than interpreting a relative error. Report the analogous full 3,072-coordinate zero-state spread, each target coordinate's local output ULP spacing in its native dtype, and measured changes in ULP units. Only report cosine similarity when both predicted and measured four-coordinate norms exceed `max(3N_s,1e−6)`; otherwise write `null`.

For each magnitude `h ∈ {.00625,.025,.1}`, also report the odd component `(median[d(+h)]−median[d(−h)])/2` and even component `(median[d(+h)]+median[d(−h)])/2`, with the corresponding odd component of the *realized-edit* rowwise predictions. This separates an approximately linear sign-changing response from a staircase, baseline drift, or asymmetric finite-step response. Compare **within** each arithmetic arm first. FP32 versus BF16 differences are suggestive only because upcasting changes all forward operations and baseline states; they do not prove that BF16 alone caused the old discrepancy. Persistent mismatch at the smallest FP32 step with stable zero baselines calls for a separate graph/derivative investigation, not an automatic v2 lens fit.

## Bounds, receipts and claim limit

One exclusive output directory per arm; create it and write the start receipt before preflight. Count preflight, MPS checks, model load, VJPs and all forward passes in each arm's clock. Cap the BF16 arm at **15 minutes** and the FP32 arm at **20 minutes**, each with **30 GiB MPS driver allocation**; stop between calls if a cap is reached, and note that an in-flight call may overshoot the wall guard. No resume, extra alpha, adaptive rerun, fallback dtype, or additional case after seeing results. The prescribed workload is at most **72 paired patch forwards, five other prompt forwards, four shared-graph VJPs and two generations per arm**. Save per-phase timings and memory peaks, all hook/source/target/dtype receipts, the full terminal vectors, selected source rows/edits/VJPs, script and protocol hashes, exception receipts, and an independently recomputable result sidecar. A resource-limited FP32 arm is an engineering limit, not evidence for or against a Jacobian lens.

This follow-up can characterize numerical behavior on **one fit-informed old-FIT direction**. It cannot establish audio-time localization, held-out transport, generated speech, a tool-call failure, a security vulnerability, or performance on the fresh v2 corpus. Do not use these diagnostics to select v2 hyperparameters or modify a frozen v2 evaluator.
