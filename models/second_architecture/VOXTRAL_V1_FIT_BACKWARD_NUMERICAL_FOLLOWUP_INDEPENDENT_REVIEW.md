# Independent static review: old-FIT numerical follow-up

**18 November 2026. Accepted as a prospective diagnostic design; implementation still needs a separate source freeze and audit before any model run.** I reviewed protocol `3576591` (SHA-256 `5778a4b84e535f7182a3daa2b973637a1c9127118ce2434ce82ba80fee467a82`) against the anchored [old-FIT pilot review](VOXTRAL_V1_FIT_BACKWARD_INDEPENDENT_RESULT_REVIEW.md) and [v2 research proposal](NEXT_PHASE_VOXTRAL_HELDOUT_PLAN.md). The pinned prior `result.json` and `details.pt` hashes match the committed files. This review did not load a model or open fresh v2 data.

The fixed beaver-recipient/monkey-donor FIT case, `word_0` row lists, two sites, four LM29 coordinates, and original BF16-derived FP32 donor-minus-recipient directions are explicit. The protocol keeps clean grad-path, no-grad, and natural-generation baselines separate. It compares BF16 and **full-pipeline FP32** arithmetic in fresh processes and requires FP32 parameters, activations and VJPs; an FP32 memory or dtype failure is recorded as an invalid arm, with no mixed-precision fallback. Because FP32 upcasts BF16 checkpoint values and changes the whole forward pass, a difference between arms cannot isolate BF16 as the cause of the pilot mismatch. The original 10% edit-fidelity value remains a diagnostic, and no Jacobian-prediction efficacy threshold is invented.

The alpha and repeat arithmetic is consistent: six nonzero signed alphas in a fixed cycle-1 order, the reverse order in cycle 2, and the original order in cycle 3. Each of the **18 nonzero alpha observations per site** has its immediately preceding alpha-zero forward. That is **36 patch forwards per site**, **72 per arm**, and **144 across both arms**, plus five other prompt forwards, four shared-graph VJPs and two greedy generations **per arm**. There are 18 zero-terminal vectors per site/arm for the prespecified repeatability floor. Both 15-minute BF16 and 20-minute FP32 clocks include preflight and load; both have a 30-GiB driver cap. The earlier BF16 pilot's ~12.0-GiB peak does not certify FP32 fit, which the protocol handles explicitly.

The proposed metric compares each forward's **realized** row edit with its own paired zero baseline. It preserves full 3,072-coordinate terminal vectors, all three repeats, a zero-state noise floor, native-dtype ULP spacing, odd/even signed-step components, and the absence of a resolved measurement. These controls are suitable for distinguishing a stable finite-step response from quantization or run-to-run drift on this one FIT case. They do not verify a reusable Jacobian lens or authorize v2 fitting.

Two implementation details should be made explicit in the frozen runner and independent auditor before execution: (1) report per-repeat `L2(p−d)` **and** the coordinatewise-median prediction-versus-median-measurement error, applying the stated `max(L2(d_median), N_s, 1e−6)` denominator to the median comparison; (2) call the final workload **72 patch forwards arranged in 36 zero/nonzero pairs per arm**, so “paired forwards” cannot be mistaken for 72 pairs. For the FP32 arm, report the selected-element unchanged fraction as an FP32 rounding observation and reserve “unchanged by BF16 cast” for the BF16 arm. These are implementation clarifications, not new outcome gates or reasons to change the fixed grid.

The follow-up remains confined to the two old v1 FIT WAVs and the anchored pilot sidecar. It must not use fresh v2 development or locked-test answers, select a new alpha after seeing results, or claim an audio-time localization or security finding from the one-case diagnostic.
