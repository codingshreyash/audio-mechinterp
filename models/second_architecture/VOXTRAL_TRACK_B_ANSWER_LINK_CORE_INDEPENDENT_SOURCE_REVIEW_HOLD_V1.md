## Blocking source issues

1. **Frozen alias order differs from V5.** V5 requires lowercase, initial-capital, uppercase, each without then with a leading space, retaining the first occurrence of any duplicate token-ID sequence. `freeze_aliases()` constructs a `set` and returns `tuple(sorted(sequences))` (lines 109–120). That sorts by token ID, losing the required surface order and first-occurrence provenance. A fake byte tokenizer returns first-token order `[32,32,32,66,66,98]` for `banana`, while the specified surface order gives `[98,32,66,32,66,32]`. Class logsumexp is order invariant, but the frozen alias inventory, per-alias records and pilot tie rule must be traceable to the prospective order. Preserve insertion order and add an order-and-duplicate regression.
2. **Per-alias gradient evidence cannot be saved by a caller.** V5 requires each clean alias's selected-row gradient or a losslessly reproducible sidecar, its finite/norm checks, and a recorded accumulation dtype. `score_alias_class()` computes `per_gradient` internally (lines 329, 362–369), then returns only the weighted aggregate `gradient` (lines 381–398). The individual gradients are discarded, so a future runner using this API cannot meet the V5 evidence contract. Return the per-alias selected-row gradients or an explicit lossless capture interface, their norms/finite status, and the accumulation dtype. The code currently uses float64 weights and an FP32 gradient accumulator, which meets the minimum arithmetic precision but does not record that choice.
3. **The claimed fixed projector width is not enforced.** V5 requires raw singleton projector output `[T,3072]`; the handoff says the core validates `[B*T,3072]`. `ProjectorHook` accepts any finite FP32 source width and checks output against that supplied width (lines 153–159, 202–205), while `capture_projector()` checks only row count and dtype (lines 289–293). The 8 fake tests use width four. The integration preflight could enforce 3072, but the current handoff's claim about this core is false. Assert the width in the production hook/capture path or narrow the handoff and require a separately reviewed runner assertion.
4. **The nominal-padding guard is unreachable.** `word_rows()` admits rows only when `160*(8*r+3) < stop <= frames` (lines 41–46), then rejects a selected row if the same center is `>= frames+200` (line 46). That second condition cannot be true. V3 requires rejection of nominally padded rows. If the PCM center rule alone establishes valid rows for the pinned processor, state and verify that invariant in preflight; otherwise check actual per-clip unpadded projector lengths and remove the dead guard. The current handoff's assertion that this helper rejects padded rows is unsupported.

## Source behavior that matches the design

The sequential scorer uses one alias per forward, feeds prompt plus `L_i−1` continuation IDs, requests `logits_to_keep=L_i`, gathers all `L_i` token log probabilities including EOS, and combines complete-sequence alias likelihoods by `logsumexp`. The source-gradient calculation uses the correct softmax-weighted sum of per-alias gradients, then donor minus recipient and a contraction over fixed word rows. `freeze_aliases()` does reject a contextual tokenization that changes the prompt prefix or continuation IDs. The flat projector hook edits every selected `b*T+r` and verifies one call, finite FP32 output, source-state equality, outside-row preservation and realized edit error. Clean/zero and natural-donor/full-donor helpers compare complete suffix IDs. The strict predicted-switch helper checks clean/zero recipient and alias coverage, negative baseline margin, predicted and measured positive margins, and an alias-covered donor generation. These fake-source checks do not prove pinned Voxtral geometry, tokenizer behavior, hook parity, gradient memory, or candidate performance.

V5 independently requires 32/32 audited human QA **before any weight load**, a reviewed admission/worker, frozen input and source hashes, old-FIT resource pilot, caps, and no-retry rules. This core has no loader or CLI and therefore makes no inference or security claim. Resolve the four source issues and rerun the fake tests before granting source GO; live execution remains separately gated.
