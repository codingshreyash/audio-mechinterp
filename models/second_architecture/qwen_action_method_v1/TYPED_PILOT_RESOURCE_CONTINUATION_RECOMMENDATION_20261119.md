# Resource continuation after the Qwen typed-pilot MPS failure

19 November 2026. **Recommendation only; no model load, new GO, or retry.** This compares placements for the one frozen `F_L1__typed` FP32 label-plus-EOS/VJP pilot. It leaves [V3 attempt 001](TYPED_PILOT_V3_FAILURE_REVIEW.md) intact and excluded. The stopped VoiceChat H100 instance is outside this plan.

## Decision

**Prefer a new, isolated 80-GB NVIDIA GPU allocation for the complete typed pilot, if one is available at an acceptable quoted rate.** Use a separate pinned Linux/CUDA source and independent executable review, then make one bounded run. This gives substantially more device-memory room than the Mac's 24-GiB MPS limit without changing FP32 weights, target scores, or the three residual-state VJPs. An H100-class GPU is specified here for its **80-GB memory**, not for a presumed speed or dollar price. The [NVIDIA specification](https://docs.nvidia.com/enterprise-reference-architectures/hgx-ai-factory-h100-h200-b200/latest/components.html) lists 80 GB per H100 SXM GPU. A 48-GB GPU may be enough but has less unmeasured transient/VJP headroom; neither option is a scientific result before its own stock/hook parity and saved audit.

If a new GPU allocation is unavailable, use a **separate CPU-only load characterization on the Mac** before a CPU full pilot. Do not immediately raise the existing MPS cap and rerun the full VJP job. The CPU path avoids the Metal allocation limit but trades it for unmeasured host RSS and time. Hugging Face documents `device_map="cpu"` and low-memory checkpoint loading; it also documents CPU/disk offload, but those are inference-oriented placement mechanisms, so backward through an offloaded model must be separately validated rather than assumed to work. [Transformers model-loading documentation](https://huggingface.co/docs/transformers/main/models).

## Evidence and its limit

| Observation | Implication |
| --- | --- |
| The [audited failed V3 attempt](TYPED_PILOT_V3_FAILURE_REVIEW.md) hit the configured 24.00-GiB MPS allocator ceiling during `from_pretrained` at 1014/1442 tensors. The error reported 16.51 GiB MPS allocated plus 7.74 GiB other allocations; 13.50 KiB more failed. No forward, score, or VJP ran. | The 24-GiB placement is insufficient **under this host/process state**. Tensor-count progress is not a memory-completion percentage. |
| That attempt had 84 process-tree RSS samples, peak 7.158 GiB, 19.524 seconds whole time, valid AC/open-lid/no-thermal host logs, and no success terminal. | It is a load failure, not a near-complete scientific pilot. The RSS sample and MPS error measure different memory categories. |
| The same pinned Qwen2.5-Omni-3B/Transformers revisions previously completed an [audited FP32 MPS FIT run](../../../eval/audio_jlens/corpus_v1/FIT_RANK16_RESULT_INDEPENDENT_REVIEW.md): 768 VJPs, 21.25-GiB peak logged Metal driver memory under a 30-GiB cap. Its [memory log](../../../eval/audio_jlens/corpus_v1/fit_rank16_transport_v1.memory.jsonl) records 18.51 GiB just after model load. | A 30-GiB cap has worked for a different, earlier workload on this host. It makes a **load-only** 30-GiB diagnostic plausible; it does not establish the new pilot's transient peak, resource safety, or target-VJP success. |
| The current Mac has 48 GiB physical RAM. At this read-only check it reported 78% system memory free but 18,864 MiB of 19,456 MiB configured swap in use. | Available physical memory looks healthy now, yet the small remaining swap reserve and lack of an in-run system-pressure trace argue against a casual local cap increase. Swap use may be historical, so it is a risk indicator rather than proof of current pressure. |

PyTorch says `torch.mps.set_per_process_memory_fraction` raises allocator OOM at the configured fraction of Metal's recommended working-set size, and that disabling the limit can cause system failure. `driver_allocated_memory()` includes cached and framework allocations, unlike tensor-only `current_allocated_memory()`. These definitions explain why allocator, process RSS, and system-free numbers must be logged separately and cannot simply be added as independent headroom. [MPS allocation limit](https://docs.pytorch.org/docs/stable/generated/torch.mps.set_per_process_memory_fraction.html), [MPS memory metrics](https://docs.pytorch.org/docs/stable/mps.html).

## Proposed staged gates, not executable approval

| Route | First stage and stop rule | Full typed pilot only if first stage passes | Cost and residual risk |
| --- | --- | --- | --- |
| **New isolated 80-GB GPU (preferred)** | Pin the exact model/checkpoint and CUDA/Transformers stack. Review a **load-only** job with an 180-second wall cap, sampled GPU allocation below 56 GiB, host RSS below 24 GiB, and no other model job on the device. Save `nvidia-smi`/framework peaks and an immutable failure receipt. A load failure stops. | New one-shot GO for exactly `F_L1__typed`; 900-second whole-job cap, sampled GPU allocation below 60 GiB, host RSS below 24 GiB, 64-MiB evidence cap, saved raw logits/states/VJPs, exact stock/read-only/leaf parity and read-only audit. Stop on OOM, nonfinite gradient, parity, deadline, or provenance failure. CUDA is a new numerical backend, so the saved comparisons are within CUDA, not presumed byte-equal to MPS. | Requires one separately billed allocation plus checkpoint staging; obtain provider quote before launch. Budget at most roughly one allocation-hour for setup, load and pilot, but **no dollar estimate is justified without a rate**. Larger VRAM improves headroom, not a guarantee of method validity. |
| **Mac CPU-only (local fallback)** | A new fixed **load-only** attempt using `device_map="cpu"`, FP32 and `low_cpu_mem_usage=True`; 300-second wall, sampled process-tree RSS below 32 GiB, system memory-free ≥25%, free configured swap ≥4 GiB, swap growth ≤256 MiB, AC/open lid/no thermal. Preserve any failure and stop before forward. | A separately reviewed 1,800-second FP32 `F_L1__typed` pilot, sampled RSS below 36 GiB, memory-free ≥20%, the same free-swap/growth and host gates, exact V3 score/parity/evidence endpoint. An initial real CPU backward must show finite gradients at both sites; no inference from a load-only pass. | No external compute bill, but unknown CPU duration and a material risk of memory pressure or thermal stop on a 48-GiB laptop. Current swap reserve would fail this proposed pre-admission until host state is healthy. |
| **Mac MPS 30-GiB diagnostic (tertiary)** | Only a *load-only* new attempt, 120-second wall, MPS allocator and sampled driver below 30 GiB, sampled RSS below 20 GiB, memory-free ≥25%, free configured swap ≥4 GiB, swap growth ≤256 MiB, AC/open lid/no thermal. Stop immediately after load and unload. Never set the MPS fraction to zero. | A complete VJP retry would need a later, separate cap and GO after load telemetry, with forward/backward memory margin justified prospectively. | No external bill and a prior 30-GiB same-checkpoint success, but current host state differs; the unified 48-GiB pool, near-full configured swap and unmeasured load transient make it less robust than an isolated GPU. |

The numerical limits above are **proposed fail-closed values**, not empirically validated safe peaks. Sampled monitors can miss short transients; a child worker needs its own deadline and a live bounded-parent handshake, as the V3 executable review already required. New placement, caps, deadlines or source bytes need a fresh fixed attempt, source review, independently bound GO and saved-result audit. The typed-only pre-human-QA exception permits only `F_L1`; the 18 speech sources and any development/locked Qwen outputs remain closed until real two-listener QA and their own reviewed runners.

## What would change the choice

- If an isolated 80-GB GPU quote is acceptable and the environment can be pinned, proceed with its load-only stage first. The already stopped VoiceChat H100 remains stopped.
- If cloud allocation is unavailable, run the CPU load-only stage after verifying healthy swap and system pressure; continue to CPU VJP only on a reviewed pass.
- A clean 30-GiB MPS load-only result with ample recorded memory and no pressure could justify considering a bounded MPS full pilot. The present 24-GiB failure alone cannot.
