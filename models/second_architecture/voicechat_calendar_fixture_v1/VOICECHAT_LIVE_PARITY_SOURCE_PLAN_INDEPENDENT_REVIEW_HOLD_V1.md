# Independent source review of the VoiceChat parity plan builder

18 November 2026. I reviewed implementation commit `4d2510e` against the amended prospective protocol `8795015` and conceptual GO `8cf7127`. Source SHA-256 values are `d542cbeb6c89219901456832a651832d026f4f3a34819f01c7559d752bfadaa4` for `live_parity_source_plan_v1.py` and `ced8193c4ff1445cffcdf0eea7f854ef37aacb54c50b5a19048e42d398dff2e9` for its original tests. **Decision: HOLD for using the source plan as a complete pre-load admission record.** This review loaded no VoiceChat weights and created no human listening record, official sample result, model output, calendar action, or security finding.

The new nine CPU fake-gate tests pass, as do 13 related low-level parity tests (22 total). The CLI does not expose test-injected checkers. The plan fixes case B/Piper, the five-stage sample/adapter/stock order, no-call placeholder hash, seed and comparison requirements, and it labels all fake-injected plans synthetic. It invokes the existing full-cohort v2 QA validator through `check_audio_qa_v2` and `read_bound_qa_receipt`, then calls the existing `preload` preflight. These are source properties; no real 12-clip QA, controller grant or external anchor exists yet.

Two blockers remain:

1. **The required `ready` → `preload` lifecycle is unproven.** The reviewed protocol requires both phases in that order, with their exact outputs archived. This builder invokes only `--phase preload` and accepts its success without a prior `ready` receipt. The preflight implementation gives the phases different checks: `ready` requires a pristine dynamic-module cache and resolves the pinned Nano metadata offline; `preload` validates the resulting generated cache and environment. A plan can therefore be emitted without evidence that `ready` ever ran. Require a bound, chronological `ready` receipt with the same source/QA/Nano/checkpoint identity, or explicitly mark `ready` as a missing future gate and do not present this output as a complete pre-load admission artifact.
2. **Input mutation during preflight can produce an internally inconsistent plan.** The builder checks the selected WAV against the frozen render before `preload`, then hashes that WAV into `selected.wav_sha256` *after* `preload` without comparing it to the frozen render again. A preload that changes the WAV returns an accepted plan whose selected WAV hash conflicts with its QA receipt. The same gap accepts a changed QA manifest and a changed official sample WAV after their earlier checks. The three exact CPU-only reproductions in `test_live_parity_source_plan_review_hold_v1.py` are marked `expectedFailure` against `4d2510e`: `Ran 3 tests ... OK (expected failures=3)`. Recheck the exact QA manifest, ledger, receipt, selected WAV, render and sample/source bytes after preflight and before writing the plan; bind the pre/post hashes and reject any drift. A later live launcher must recheck again before every model process.

This source-only builder is narrower than the conceptual protocol's full fresh-process orchestration. It does not run the unchanged official sample, reset and compare four model arms, enforce GPU/runtime/output caps, or save raw pass data. The handoff acknowledges those gaps. Correcting the two source-plan blockers would justify a GO for this **plan builder only**, not a live parity or model-behavior conclusion. The full live launcher still needs its own source review and external freeze.
