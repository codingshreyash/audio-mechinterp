# VoiceChat H200 memory trajectory: pinned-source audit

19 November 2026. **Source supports a length-dependent memory hypothesis, not a diagnosed leak.** I fetched four files from NVIDIA-NeMo/Speech at pinned commit `097dfe9e2f55baf653b83035868bdc89849f1b47`; their SHA-256s match the local five-file source pin: `nemotron_voicechat.py` `fe11dcdde3c31d7144469dab0c6ec9629ff8f7e4dbf881d8d1db258243a67f80`, `duplex_stt_model.py` `415e1e01584bab96d9c059d5b0fe9162adaf19677ef43e565c3afad6e073e74b`, `offline_voicechat.py` `ebde701baec12a014443eac36262a6af7a7a62b3e052f1c4a387db6aaad8da44`, and `offline_voicechat_fc_infer.py` `797a80d9cef654550514e045a9388ca689a25dc9bbf70436eb117d249a17644f`.

The official function-call helper first runs `offline_inference(..., decode_audio=False)` to detect calls; only after that pass completes can it parse a call and run a second pass with an injected response. [Pinned helper](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/inference/utils/offline_voicechat.py#L171-L289). VoiceChat's `@torch.no_grad()` loop calls `stt_model._step_inference` and TTS `infer_codes_one_step` at every step; TTS explicitly carries `past_key_values`. [Pinned VoiceChat loop](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/models/nemotron_voicechat.py#L544-L709). The STT initializer disables its cache for the Nemotron backbone, and the no-cache branch passes all fused embeddings through position `t` to the model. Its forward projects the full returned hidden sequence into text logits and, when enabled, separate function and ASR logits. [Cache choice](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/models/duplex_stt_model.py#L3715-L3725), [full-prefix branch](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/models/duplex_stt_model.py#L3979-L4032), [logit projections](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/models/duplex_stt_model.py#L466-L550).

Those operations can make *temporary* per-step allocations grow with sequence length; the TTS cache can also increase *live* allocations. The full-history STT branch does **not** itself prove retained activations or a leak, and `@torch.no_grad()` means normal autograd graph accumulation is not the obvious explanation. The saved H200 evidence contains only one sampled peak (130,540 MiB at termination) and coarse 50-step log milestones through 650/859, so it cannot separate live tensors, allocator reservation, temporary peaks, or non-PyTorch GPU allocations. [PyTorch's CUDA memory guide](https://docs.pytorch.org/docs/stable/notes/cuda.html#memory-management) explains why `nvidia-smi`/reserved memory alone is not a leak test; its [memory debugging guide](https://docs.pytorch.org/docs/stable/torch_cuda_memory) notes that its allocator trace excludes direct CUDA allocations.

**Cheapest discriminating prospective diagnostic:** Do source-only shape accounting first, using the pinned config and the `B × (t+1) × vocabulary` logits at representative steps; this costs no GPU but cannot establish actual allocator behavior. If still warranted, make one **diagnostic-only** H200 replay of the pinned public sample with a reviewed wrapper that stops just after step 400, below the previous step-650 cap event. Keep the checkpoint, prompt, audio, model code, 130,000-MiB GPU cap, finite wall/evidence caps, and stub-only tool context unchanged. At steps 50, 100, 200, 300, and 400, synchronize CUDA and write bounded numeric records: `memory_allocated`, `memory_reserved`, per-interval `max_memory_allocated`, NVML process memory, and total elements/shapes of carried TTS cache and inference-state tensors. Do not dump weights, activations, audio, or generated content. Use a fresh output ID, source review, freeze, and seal; this is not a behavior test.

Interpret the trace narrowly: flat live allocated memory with rising interval peaks points toward length-dependent temporary work; rising live allocated memory accounted for by cache/state points toward intended retained state; rising live memory without that accounting calls for a bounded allocator snapshot/ownership audit before using the word *leak*. A large NVML-minus-PyTorch gap suggests allocations outside the PyTorch allocator. A step-400 trace still cannot predict the final peak at 859. A second full run or a higher H200 cap is not justified by the existing single-peak record. Even a completed pass 1 would leave the possible pass 2 unmeasured.
