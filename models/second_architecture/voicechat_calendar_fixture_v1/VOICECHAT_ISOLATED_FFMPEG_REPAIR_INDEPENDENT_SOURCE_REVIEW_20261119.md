# Independent source review: isolated FFmpeg repair

19 November 2026. Reviewed plan commit `717108d` against the immutable public-sample attempt 003, without running a model or changing the cloud host.

## Decision

**GO** for read-only host/package inspection, an apt dry run, exact-version `amd64` package downloads and extraction under the task-local prefix, recursive linkage inspection, and a fresh-process **no-model** `torchaudio.load` plus `AudioDecoder` smoke against the pinned public WAV. **HOLD** on any VoiceChat model execution, system-wide `apt install`, Python-package change, calendar audio, or change of FFmpeg version/distribution. A new model run needs a reviewed runner that binds native library bytes and resolves their actual paths, then a fresh freeze and independent source review.

## Basis

Attempt 003 reached the official child, initialized `function_head`, loaded 1,617 checkpoint tensors, and printed `Model ready.` Its exception then occurred at `load_wav_16k_mono` → `torchaudio.load` → TorchCodec, where every FFmpeg backend failed to find its corresponding `libavutil.so` (`.60` through `.56`). This proves an immediate missing-library blocker, not a CUDA failure or a successful inference. The saved run has no generated audio or response. [Saved stderr](runs/public_sample_existing_a100_attempt_003/voicechat-sample-output-003/stderr.log), [independent attempt audit](VOICECHAT_EXISTING_A100_SAMPLE_ATTEMPT_003_INDEPENDENT_AUDIT_20261119.md).

The [TorchCodec 0.10 release](https://github.com/meta-pytorch/torchcodec/releases/tag/v0.10.0) states compatibility with PyTorch 2.10; the host has `torch==2.10.0+cu128` and `torchcodec==0.10.0`. Its [tagged installation guidance](https://github.com/meta-pytorch/torchcodec/blob/v0.10.0/README.md#installing-torchcodec) supports FFmpeg majors 4–8 and requires separately loadable FFmpeg libraries. The tagged README's compatibility table stops at 0.9, so the release note is the specific source for the 0.10/2.10 pair. Ubuntu lists Jammy `libavutil56`, `libavformat58`, `libswresample3`, and `libswscale5` at `7:4.4.2-0ubuntu0.22.04.1`; [Jammy's `libavcodec58` listing](https://packages.ubuntu.com/search?keywords=libavcodec58) includes that same `amd64` version. This supports FFmpeg 4.4.2 as a coherent candidate, not proof that the host's apt indexes still offer it. [Ubuntu libavutil56](https://packages.ubuntu.com/jammy-updates/libavutil56), [libavformat58](https://packages.ubuntu.com/jammy-updates/libavformat58), [libswresample3](https://packages.ubuntu.com/jammy-updates/libswresample3), [libswscale5](https://packages.ubuntu.com/jammy-updates/libswscale5).

## Conditions for the GO portion

1. Confirm the host OS, architecture, apt origins, exact candidate versions, and available disk space. Record apt's proposed dependency set. Use the pinned Jammy version from configured Ubuntu repositories; stop if it is unavailable or would entail a distribution or system-library replacement. The five named archives are only a starting set: Jammy `libavformat58` alone declares additional dependencies such as `libbluray2`, `libchromaprint1`, and `libgnutls30`.
2. Record the SHA-256 and `dpkg-deb` package name, version, architecture, dependencies, and file listing for each downloaded archive before extraction. Reject unexpected paths/symlinks. Extract only within the task prefix. Preserve existing CUDA library lookup in the child environment.
3. Check `libtorchcodec_core4.so` and the extracted libraries with `readelf` and `ldd`; resolve and record **all** non-system native dependencies actually loaded from the prefix, not only `libav*.so.*`. Stop on unresolved or unapproved paths. `ldd` alone does not prove the symbols or decoder work.
4. Run the plan's exact `torchaudio.load` path and direct `AudioDecoder` check in a *new* Python process with the library path set before startup. Compare the public WAV's SHA-256 with the pinned `265f9e5f58bff1e71f4354f7d83e2ff405a8405b29c2cfeb50eb9085042e9136`; retain stdout, stderr, exit status, package and resolved-library receipts. If decode fails, capture the new traceback and stop. If it passes, report only that the no-model audio decode works.

The plan's proposed `native_ffmpeg_runtime` receipt is necessary because the V3 freeze binds the *text* of `LD_LIBRARY_PATH` and the Python package inventory, but not the external `.so` bytes. At the eventual model gate, it should bind every package and resolved prefix-library hash, absolute paths, and effective environment, then recheck them at launch. The `pydub` executable warning is separate from this failure; it may matter later and is not resolved merely by passing this smoke.
