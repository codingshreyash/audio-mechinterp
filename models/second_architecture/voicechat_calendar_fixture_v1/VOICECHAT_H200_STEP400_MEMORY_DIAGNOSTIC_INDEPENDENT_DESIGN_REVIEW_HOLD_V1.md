# Independent design review: VoiceChat H200 step-400 diagnostic V1

19 November 2026. **HOLD on implementation freeze and GPU launch.** This is a source-only review of `VOICECHAT_H200_STEP400_MEMORY_DIAGNOSTIC_PROSPECTIVE_V1.md` at commit `4b20dc2`. It is not an executable review, host freeze, or GO. I loaded no VoiceChat weights and started no instance.

## What checks out

The pinned [VoiceChat inference loop](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/models/nemotron_voicechat.py#L671-L729) calls STT `_step_inference` and then TTS `infer_codes_one_step` at each `t` in `range(1,T)`. The TTS result is assigned to `code, past_key_values` immediately before `gen_codes[:,t] = ...`. A wrapper of that one model instance can therefore observe the returned cache at the specified post-TTS, pre-write boundary, and a dedicated exception there can stop at `t=400` before the function-call helper receives a first-pass result. The pinned [official helper](https://github.com/NVIDIA-NeMo/Speech/blob/097dfe9e2f55baf653b83035868bdc89849f1b47/nemo/collections/speechlm2/inference/utils/offline_voicechat.py#L171-L289) calls the first pass with `decode_audio=False` and only parses or starts pass 2 after it returns. The V1 document correctly requires comparison of the wrapper's exact first-pass arguments, preservation of the model source, and an invalid record for any partial run.

The H200 saved attempt establishes a model load and progress through step 650/859, followed by a sampled 130,540-MiB resource stop against the reviewed 130,000-MiB cap. It does not contain a completed answer or enough time-resolved memory observations to diagnose a leak. The proposed short trace asks a distinct, testable question. Its 130,000-MiB, 1,800-second, 30-GiB free-disk, 64-MiB evidence, process-group watchdog, and first-pass-only stop requirements are bounded in source. Missing NVML telemetry is specified as a failure. These checks do not establish that the unimplemented wrapper actually enforces them.

## Two corrections before executable design review

1. **Define the first peak interval.** V1 says every maximum covers the interval since the previous checkpoint, but there is no previous checkpoint at `t=1`. Unless peak counters are reset after model load and before pass-1 generation, the first `max_memory_allocated`/`max_memory_reserved` values can include checkpoint loading and warmup. Fix the reset point, record a pre-loop baseline, and say whether the first interval is comparable to the later intervals. Keep every later reset after the synchronized snapshot is recorded.
2. **Count shared storage once across families.** V1 asks for de-duplicated storage bytes *per named family* and then proposes comparing carried state to live PyTorch allocation. A storage object reachable from both the inference-state tree and TTS cache can be counted twice in that sum. Require one global unique-storage total in addition to per-family logical and unique totals, and mark the total incomplete if either traversal has an unknown container. No tensor values or storage addresses should enter durable evidence.

The eventual implementation review must also verify actual parent NVML polling gaps and process-group stop behavior under fake-model and telemetry failures; the V1 statement of a 0.2-second sampling interval is a requirement, not evidence that it happened. Inspect whether the wrapper's instance-method replacements preserve argument and return identity, execute each original once, release transient references, and prevent a second pass on any unexpected `T` or stop failure.

**Verdict:** The probe boundary and overall diagnostic are feasible from pinned source, but V1's first peak and carried-storage accounting are underspecified for the proposed interpretation. Correct them in an amendment, then obtain an independent source review of the revised design before writing an executable or starting compute. A completed short trace would still be a memory-accounting result, not a model behavior or security result.
