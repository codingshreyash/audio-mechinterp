# Independent review: Voxtral fit smoke

I audited [VOXTRAL_PLAN.md](VOXTRAL_PLAN.md), [typed prompt v2](TYPED_PROMPT_V2.md), [voxtral_smoke.py](voxtral_smoke.py), the saved [v1 runs](runs/voxtral_smoke_v1/), and [v2 typed runs](runs/voxtral_typed_prompt_v2_fit/) without running MPS or opening development/test inputs. All run artifacts are fit-only Piper red/blue or typed equivalents.

| Input and protocol | Red complete answer / EOS / exact score | Blue complete answer / EOS / exact score |
| --- | --- | --- |
| Audio, v1 (two runs per color) | `Red`, yes, pass **2/2** | `Blue`, yes, pass **2/2** |
| Typed, v1 (one run per color) | `Red`, yes, pass **1/1** | `**Blue**`, yes, **fail 0/1** |
| Typed, v2 fit repair (two runs per color) | `Red`, yes, pass **2/2** | `Blue`, yes, pass **2/2** |

I recomputed the script's exact-one-color-word regex from every saved full answer, checked the generated token counts/IDs and EOS stop flags, and compared repeated prompt-token and output-token sequences. Every repetition within a condition has identical prompt IDs and generated IDs. Audio Red emits `[12846, 2]`; audio Blue emits `[24851, 2]`. The v1 typed Blue result emits `[1438, 24851, 1438, 2]` and decodes to `**Blue**`; it cannot be counted as an exact one-word pass. V2's added no-Markdown/no-punctuation sentence is recorded verbatim and with a correct SHA-256 in each typed result. Its protocol file predates the v2 result files by local modification time, but that chronology is not an immutable preregistration record. V2 success is a **fit-only repair**, not a retroactive v1 pass or an independent transfer result.

Every saved run matches the pinned red/blue manifest hash and dependency freeze hash. The four audio runs match their current Piper WAV SHA-256 values and use the same audio instruction; processor metadata records 375 audio placeholders and `[1, 128, 3000]` mel features. Typed runs contain zero audio placeholders and no audio features. All reports agree on `mistralai/Voxtral-Mini-3B-2507` revision `3060fe34b35ba5d44202ce9ff3c097642914f8f3`, config/index/tree hashes, shard sizes, greedy generation (`max_new_tokens=32`), and EOS token 2. The local snapshot validator reproduces the saved snapshot records, including revision metadata and shard **sizes**. It does not hash the large shard contents. The installed Transformers wheel is checked by `5.20.2` version and associated with release tag `18329f…`; the exact wheel source commit is not independently attested by these reports.

The first audio Red result has no in-file script hash; [FIRST_AUDIO_PROVENANCE.json](runs/voxtral_smoke_v1/FIRST_AUDIO_PROVENANCE.json) correctly binds its result SHA to the saved [first-audio source snapshot](source_snapshots/voxtral_smoke_first_audio.py). That snapshot and provenance note were created after the result, so they support reconstruction but cannot prove the source was frozen before execution. The first audio Blue and first typed runs record an earlier script SHA (`334789f2…`) whose exact source file is not retained here. Both second audio runs and all four v2 typed runs record SHA `ba5f21cc…`, matching the current script. These provenance limits do not change the saved outputs, but they narrow source-level reproducibility of the earliest runs.

Observed peak MPS driver allocation is about **9.93 GiB** for audio and **8.73 GiB** for typed runs, below the 30 GiB ceiling; all runs report normal EOS. This is an inference and answer-format gate for a second audio-to-text architecture. It does not yet establish a causal internal mechanism, native speech-output behavior, or a security finding.
