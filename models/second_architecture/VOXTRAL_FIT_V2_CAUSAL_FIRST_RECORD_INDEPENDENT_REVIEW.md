**18 November 2026.** Reviewed `voxtral_fit_v2_causal_first_record.py` and its CPU tests against the committed FIT-only design and mask artifact. This review did not load Voxtral model weights or run MPS. Development and locked-test inputs/answers were not used.

## Verified

- Literal SHA-256 bindings for the design, masks, v2 selection, index, v2 gate/result, and reused v1 runner match the files on disk. CPU `--validate-only` passes and reports only `animal_08/piper/fit_chosen` with the two selected WAVs, `beaver` and `monkey`; it verifies their bytes and processor prompt IDs against the saved natural pilot. The runner now asserts raw BF16 dtype/shape at capture and patch time, edited row BF16 shape, exactly one hook after generation, then exactly one more after each of two teacher-forced scores. It records hook events and source hashes.
- The complete-answer classifier enforces a single final EOS, rejects any earlier/nonterminal special token and malformed surface, and uses casefolded single alphabetic words. The two teacher-forced canonical candidate+EOS scores use the frozen tokenizer sequences through the audited v1 scoring function. Restoration and loss each use their specified base/donor; off-word controls use one FP32 norm scale and check realized BF16 edit norm within 5%; random direction is seeded from the declared SHA-256 label.
- The **planned** first-record arithmetic is 80 arm/site/direction patch generations +4 opposite-word controls +8 passive-hook replays +2 blank baselines +6 feature inputs = **100 generations**, plus **8 source captures** and **200 teacher-forced forwards**. Output directory creation is exclusive, progress is append-only with fsync, and result/error JSON files refuse overwrite. The 45-minute and 30-GiB guards are present; fixed preflight/load and measured per-record time enter the eight-record projection. The benchmark does not continue to the other seven FIT records.

## Resource-gate issue found in the first draft and resolved

An invalid norm control writes `invalid_condition` and skips its generation and two candidate-score forwards. The first draft multiplied the *observed* variable time by eight without checking that all 100 generations and 200 scores were timed. This could understate later-record cost. The revised runner counts captures, generations, scores, and invalid conditions, requires **108 planned progress records**, and sets `passes=false` with no projected time unless the first record actually completes all **8 captures, 100 generations, and 200 scores with zero invalids**. I inspected the fail-closed implementation and its CPU test.
