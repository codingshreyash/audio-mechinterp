# Voxtral Track B V6 MPS runtime adapter: source-only handoff

**HOLD for model weights and pilot execution.** The [runtime adapter](voxtral_track_b_v6_mps_runtime_adapter_source_v1.py) is a separate, fake-tested process and memory boundary. Its public `launch_v6_pilot()` always rejects. It has no candidate loader, processor invocation or callable composition with the [pre-pilot launcher](voxtral_track_b_v6_pre_pilot_launcher_source_v1.py) and [worker](voxtral_track_b_v6_pilot_worker_source_v1.py). The existing launcher verifies externally pinned W/A/R bytes, actual `candidate_common.qa_gate` results, and the fresh no-weight source/processor/checkpoint/host fingerprints; a later reviewed adapter must invoke those checks before the private process path. It must pass a top-level, spawn-pickleable worker operation whose loader uses the pinned local Voxtral snapshot, `torch.float32`, MPS and eval mode, and rechecks the model/processor/source hashes before inference. An arbitrary injected operation in the present private test helper does not establish those properties.

In the spawned child, `configure_mps_allocator()` obtains `torch.mps.recommended_max_memory()` and calls `torch.mps.set_per_process_memory_fraction(30*2**30/recommended)` **before** the operation. It rejects a device whose recommended memory is below 30 GiB. The receipt records recommended bytes, configured bytes and fraction. That setting is an allocator-enforced ceiling for PyTorch MPS allocations, not a measured exact device peak or a guarantee about non-PyTorch use. A bounded sampler polls `torch.mps.driver_allocated_memory()` every 20 ms while the operation runs and tracks observations by active worker call ordinal; it synchronizes and samples at finish. The **sampled high-water is a lower bound** on transient usage. It is never reported as an exact peak. The worker's own post-call observation remains separate.

The parent writes an exclusive `campaign_claim_path + '.watchdog'` marker before spawning, so a timeout/OOM/crash cannot be retried under the same externally bound campaign claim in another output directory. The child retains any partial worker directory and call ledger. The parent joins with the remaining 240-second total deadline, terminates then kills a still-running child, and writes an exclusive adjacent result. The deadline starts before spawn and includes child setup, cap configuration and any eventual model load. A result written after the deadline is marked timeout. The parent claim is distinct from the worker's exclusive claim, which the child would create before its schedule. The parent must never remove either claim on failure.

## Live blockers

- Real 32/32 QA, externally reviewed admission/review and frozen W/A/R launcher pins remain absent. Public launch is hard HOLD before any supplied loader.
- The private child currently accepts an arbitrary fake operation and optional fake MPS object. A reviewed top-level operation must construct exact old-FIT and synthetic batches from the bound no-weight preflight, call a pinned FP32 Voxtral loader and processor, validate parameters/device/eval state, provide a verified host probe, and delegate to the worker. The production MPS module is imported inside the child so it need not be pickled. No closure/lambda operation may be used with spawn.
- Sampled driver allocation can miss sub-20-ms spikes; source review must decide whether the MPS allocator fraction sufficiently certifies V6's 30-GiB bound and whether independent system-level memory evidence is needed. The worker's current receipt still sets `measured_mps_high_water_present=false` and `hard_per_call_watchdog_present=false`; it cannot be relabeled as a V6 measured GO merely because this adapter exists.
- Parent result and child worker ledger require a saved-data auditor, independent post-run host-log check, and post-pilot independent GO. The existing source-only admission review does not authorize inference.

Verification: [six fake tests](test_voxtral_track_b_v6_mps_runtime_adapter_source_v1.py) cover allocator fraction and insufficient recommended memory, partial live ledger row sampling, spawned fake completion, no retry at another output path, fake OOM, hard timeout/claim retention, and public HOLD. No candidate model, real processor, WAV or GPU was used.
