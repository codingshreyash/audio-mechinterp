## Remaining blocker before `ready` or model loading

**The executable dynamic-module cache is not pinned.** `check_nano_cache()` constrains `HF_HOME/hub` but never checks `HF_HOME/modules`. In the pinned [Transformers loader](https://github.com/huggingface/transformers/blob/v4.56.0/src/transformers/dynamic_module_utils.py#L417-L445), remote-repository Python is copied into a commit-named dynamic-module directory **only if the target file is absent**. A preexisting modified file under that directory can therefore be imported by `verify_nano_offline()` although the six hub snapshot hashes match. A synthetic cache with all six expected snapshot files, correct ref, and an extra `modules/transformers_modules/.../modeling_nemotron_h.py` still returned `nano_files_verified=6`. This is a provenance and code-execution gap, not a model finding. Require an absent/empty dedicated modules cache before resolution and verify the copied dynamic-module Python hashes afterward (including any relative imports), or otherwise prove exact bytes before import. Add a negative self-test for a preseeded module.

The current “no Nano weights” cache claim also overlooks direct extra entries under the Nano repository cache root. A synthetic `repo/model.safetensors` alongside the six good files still passed `check_nano_cache()`. Require an explicit repository-root allowlist, normally `refs`, `snapshots`, and `blobs` for this staged cache, and reject extra files/directories. The existing blob-set and snapshot-set checks already reject weight files in those two locations.

**Decision:** no source-review objection to the corrected fixture and NeMo checks, but **do not treat `ready` as an executable-code or no-weights clearance** until the two Nano cache gaps are closed and re-reviewed. Later offline resolution may reveal additional runtime dependencies; the full VoiceChat load and no-hook/passive-hook identity pilot remain separate gates before any fixture result.
